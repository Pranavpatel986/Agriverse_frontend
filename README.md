# AgriVerse — Frontend

Next.js (App Router) frontend for the AgriVerse agricultural knowledge platform, built against the AgriVerse REST API.

## Stack

Next.js · TypeScript · Tailwind CSS v4 · Shadcn-style components (hand-authored, see below) · TanStack Query · React Hook Form + Zod · Axios · Vitest + React Testing Library

## Getting started

```bash
npm install
cp .env.example .env.local   # edit NEXT_PUBLIC_API_BASE_URL if your backend isn't on localhost:8081
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). See `.env.example` for what each variable does.

## Architecture

Feature-based, not type-based — see `src/features/*` for each vertical (auth, articles, comments, roadmaps, quiz, admin, etc.), each with its own `api/` (typed service methods), `hooks/` (TanStack Query), `types/`, and `components/`. `src/shared/` holds only what's proven reused across ≥2 features: UI primitives (`shared/components/ui`), composite patterns like `DetailPanel`/`CropPicker`/`Pagination` (`shared/components/composite`), and cross-cutting infra (`shared/lib/api`, `shared/lib/auth`, `shared/lib/query`).

### Auth

Access tokens live in memory only (never localStorage). The refresh token is held server-side in an httpOnly cookie managed by this app's own Route Handlers (`src/app/api/auth/*`) — a BFF layer that exists because the backend returns the refresh token as plain JSON rather than setting its own cookie. See the doc comments in `shared/lib/auth/refresh-cookie.ts` and `shared/lib/api/client.ts` for the full reasoning.

`src/proxy.ts` (Next.js 16's renamed `middleware.ts`) does a fast, best-effort edge redirect for protected routes; `features/auth/components/auth-gate.tsx` is the authoritative client-side check behind it. Neither is the real security boundary — that's the backend's own per-endpoint authorization.

### UI primitives

`shared/components/ui/*` are hand-authored in shadcn's conventions (Radix + `class-variance-authority`) rather than generated by the shadcn CLI, since `ui.shadcn.com` isn't reachable from every environment this was built in. Functionally equivalent; just copy-pasteable the same way shadcn components normally are if you want to diff against upstream later.

## Testing

Vitest + React Testing Library, colocated `*.test.ts(x)` files next to the source they cover. Current coverage is deliberately weighted toward pure, high-value logic rather than exhaustive component coverage:

- `shared/lib/api/error.ts` — the error-normalization layer every API call funnels through
- `shared/lib/auth/{jwt,token-storage}.ts` — token handling
- `shared/lib/utils.ts` — formatting/slug helpers
- `features/auth/schemas/auth.schema.ts` — password/email validation rules
- `shared/hooks/use-debounced-value.ts`
- `shared/components/composite/pagination.tsx` — the windowing/boundary logic

This is a foundation, not full coverage — the natural next additions are the roadmap step-status inference (`features/roadmaps/components/roadmap-step-list.tsx`), the BFF route handlers (need a request-mocking setup, e.g. `next-test-api-route-handler`), and end-to-end coverage of the auth flow (Playwright) since that spans both the client and the Route Handlers.

## Roadmap — what's next

Checked against §10.1 of the Software Architecture Document (Role & Permission Matrix): content creation is **Author/Editor/Admin**, with Authors restricted to their own articles and Editor/Admin able to publish/edit any article. Reader cannot create content.

- [x] **Article authoring (Create)** — Author/Editor/Admin, gated per §10.1's Role & Permission Matrix. Block-based editor matching the `{blocks: [...]}` body shape (heading/paragraph/image/table/FAQ) at `/dashboard/articles/new`. `tagIds` always sends `[]` — no endpoint exists to resolve tag names to ids.
- [ ] **Article authoring (Edit)** — still blocked on the same backend gap: no endpoint to fetch a single article's full content by id. `features/articles/components/article-form.tsx` is written so adding an `editing` prop later is straightforward, the same pattern SchemeForm/DiseaseForm/MachineryForm already use.
- [ ] `/forgot-password`, `/reset-password`, `/verify-email` pages (schemas/services already exist, pages don't)
- [ ] Reader-facing Profile page (page #5 of the original spec, never built)
- [ ] Notifications (full API exists — list/read/delete/unread-count — no UI at all)
- [ ] Comment replies + comment edit/delete UI (services exist, no UI)
- [ ] `error.tsx` / `not-found.tsx` / `loading.tsx` at route level, `sitemap.ts`/`robots.ts`, real OG image, real favicon

See the "Known gaps / open questions" section below for gaps that are backend-dependent rather than frontend work.

## Known gaps / open questions

These are flagged in code comments at their exact location, not silently worked around:

- **Roadmap progress** is a count (`completedSteps`), not per-step completion flags — the UI infers a sequential unlock model, which may not match the backend's actual intent.
- **Weather forecast shape** is an untyped `JsonNode` in the API — `WeatherCard` reads a plausible shape defensively.
- **No saved-locations endpoint** exists for Weather, despite the frontend spec calling for one.
- **Article detail** is missing `heroImageUrl`/`publishedAt`/`readingTimeMinutes`/`subtitle` in the documented API response, despite the frontend needing them for SEO/display — handled as optional fields.
- **Bookmark un-save from the Article page** isn't possible — there's no delete-by-entity-id endpoint, only delete-by-bookmark-id (which the Article page doesn't have).
- Several filter option lists (disease severity/pathogen type, scheme beneficiary type, machinery category) have no backend-enforced enum — placeholder values are used, flagged in comments.
- Social login and newsletter signup are UI-complete but not wired to anything real — no OAuth client credentials or `/newsletter` endpoint exist yet.
